API reference

Every function, setter, enum and callback a user of the package can reach — 766 of them — read straight out of the source. All of it lives in the Tweeny namespace.

Reading the signatures

@ marks a handle (a reference to an object), &in a read-only parameter passed by reference, and = value a default you can leave out. Anything returning a tween type returns the tween itself, so it can be chained.

Entry points and global control

This is the front door of Tweeny: the free functions in the Tweeny namespace that create tweens from a getter/setter pair, drive the clock, read and write project-wide state, and run an operation over every tween matching a target or id. Everything routes through a single lazily created TweenyManager reached with Manager(), whose public fields hold the defaults copied onto each new tween and the global time scales applied on every tick. The package bootstraps itself: TweenySettings is a ProjectSetting that pushes the inspector values into the manager and spawns an immutable TweenyRunner entity at play start, which calls TickPhase for the Normal, Late and Fixed phases. Nothing drives UpdateType::Manual, which is what ManualUpdate is for — tests and the editor preview advance those tweens with a delta they choose.

Examples

Tween a value of your own and step it deterministically, which is what UpdateType::Manual plus ManualUpdate exists for.

angelscript 
using namespace Tweeny;

class HealthBar : CometBehaviour
{
    float fill = 0.0f;

    float GetFill() { return fill; }
    void SetFill(float value) { fill = value; }

    void Start()
    {
        To(FloatGetter(this.GetFill), FloatSetter(this.SetFill), 1.0f, 0.5f)
            .SetId("hud")
            .SetUpdate(UpdateType::Manual);

        // Nothing drives Manual tweens, so advance them in slices of our choosing.
        for (int i = 0; i < 5; i++) {
            ManualUpdate(0.1f, 0.1f);
        }
    }
}

Global control around a pause menu: freeze everything, run the menu, then snap it away by id.

angelscript 
using namespace Tweeny;

void OpenPauseMenu(Transform@ menuRoot)
{
    PauseAll();
    SetTimeScale(1.0f);
    Move(menuRoot, Vector2(0.0f, 0.0f), 0.3f).SetId("menu");
}

void ClosePauseMenu()
{
    Kill("menu", true);   // apply the end value, then drop the tween
    PlayAll();            // resume everything that was paused
}

Reaching an operation that has no id overload through Apply, and walking the tweens on one target.

angelscript 
using namespace Tweeny;

void RestartHudTweens()
{
    // There is no Restart(const string&in) overload, so go through Apply.
    int touched = Apply(TweenOperation::OpRestart, FilterType::TargetOrId, null, "hud", -999, 0.0f, true);
    Debug::Log("restarted " + touched + " hud tweens");
}

void StopSpinner(Transform@ spinner)
{
    if (!IsTweening(spinner, true)) {
        return;
    }
    array<ITween@>@ live = TweensByTarget(spinner, true);
    for (uint i = 0; i < live.length(); i++) {
        live[i].Complete(false);
    }
}

Things that catch people out

  • SetTimeScale is not just for scaled tweens: TweenyManager::Tick computes unscaled = unscaledDeltaTime * unscaledTimeScale * globalTimeScale, so setting the global time scale to 0 freezes tweens marked timescale-independent as well. Only Manager().unscaledTimeScale is exclusive to them.
  • ManualUpdate advances *only* tweens whose update type is UpdateType::Manual — Tick skips any tween whose GetUpdateType() differs from the phase. Tweens left on Normal/Late/Fixed keep being driven by the runner no matter how you call ManualUpdate.
  • Sequence() does not go through ApplyDefaults. It copies only defaultAutoKill, defaultUpdateType and defaultTimeScaleIndependent, so defaultEase, the ease params and defaultLoopType never reach a sequence, and it auto-plays only when defaultAutoPlay is All or AutoPlaySequences.
  • The last parameter of Apply means a different thing per operation: includeDelay for OpRewind/OpRestart, withCallbacks for OpComplete, complete for OpKill, andPlay for OpGoto, and it is ignored by the rest.
  • Apply invokes goto as tween.Goto(gotoPosition, flag, false), so Goto, GotoAll and OpGoto never fire the callbacks between the old and new position. Call ITween::Goto(to, andPlay, withCallbacks) on the tween itself if you need them.
  • Overload coverage is uneven: only Play, Pause and Kill accept a string or int id. TogglePause, PlayForward, PlayBackwards, Rewind, SmoothRewind, Restart, Complete, Flip and Goto take Object@ only — go through Apply(..., FilterType::TargetOrId, null, "myId", -999, ...) to reach them by id.

Tween settings, callbacks and playback

This area covers the type-agnostic face of every Tweeny tween: the ITween interface the scheduler holds, and the TweenCore mixin that supplies its entire implementation. It owns the timing and looping state machine (position, delay, loop count, loop type, time scale), the easing configuration, the playback verbs (Play, Pause, Goto, Rewind, Restart, Complete, Kill, Flip), the read-only progress queries, and the nine callback slots. Because AngelScript has no generics, TweenCore is included as a mixin by one concrete class per value type (TweenFloat, TweenVector3, …); each concrete class wraps the CoreSetX validators in one-line fluent SetX methods that return its own type so chaining works. Every operation — ticking, seeking, rewinding, completing, sequence playback — funnels through a single internal DoGotoInternal, which is why callback firing rules are uniform across all of them.

Examples

Configure a tween with ease, delay, looping and a completion callback, then drive it manually later.

angelscript 
using namespace CometEngine;
using namespace Tweeny;

class DoorPanel
{
    Transform@ panel;
    TweenVector3@ slide;
    bool settled = false;

    void Open()
    {
        @slide = Move(panel, Vector3(0.0f, 3.0f, 0.0f), 0.6f)
            .SetEase(Ease::OutBack, 1.4f)
            .SetDelay(0.2f)
            .SetLoops(2, LoopType::Yoyo)
            .SetAutoKill(false)
            .SetId("door")
            .SetUpdate(UpdateType::Normal, true)
            .OnComplete(TweenCallback(this.OnSettled));
    }

    void OnSettled()
    {
        settled = true;
    }

    void Close()
    {
        // Auto-kill was disabled at creation, so the handle is still usable here.
        slide.PlayBackwards();
    }
}

{
    array<ITween@> suspended;

    void OnMenuOpened(array<ITween@>@ running)
    {
        for (uint i = 0; i < running.length(); i++) {
            ITween@ tween = running[i];
            if (tween.IsActive() && tween.IsPlaying() && !tween.IsIndependentUpdate()) {
                tween.Pause();
                suspended.insertLast(tween);
            }
        }
    }

    void OnMenuClosed()
    {
        for (uint i = 0; i < suspended.length(); i++) {
            if (suspended[i].IsActive()) {
                suspended[i].Play();
            }
        }
        suspended.resize(0);
    }
}

An infinite yoyo pulse with a per-cycle callback, retimed and stopped at runtime.

angelscript 
using namespace Tweeny;

class Pulse
{
    float glow = 0.0f;
    TweenFloat@ pulse;
    int beats = 0;

    float GetGlow() { return glow; }
    void SetGlow(float value) { glow = value; }

    void Begin()
    {
        @pulse = To(FloatGetter(this.GetGlow), FloatSetter(this.SetGlow), 1.0f, 0.5f)
            .SetEase(Ease::InOutSine)
            .SetLoops(-1, LoopType::Yoyo)
            .OnStepComplete(TweenCallback(this.OnBeat))
            .OnKill(TweenCallback(this.OnStopped));
    }

    void OnBeat() { beats++; }
    void OnStopped() { glow = 0.0f; }

    void HalfSpeed()
    {
        // SetTimeScale is never blocked by the creation lock, unlike SetLoops or SetDelay.
        pulse.SetTimeScale(0.5f);
    }

    void Stop()
    {
        // Complete() is a no-op on an infinite tween, so kill it instead.
        pulse.Kill(false);
    }
}

Things that catch people out

  • Six settings are frozen by the creation lock: CoreSetLoops, CoreSetDelay, CoreSetRelative, CoreSetSpeedBased, CoreSetAutoKill and CoreSetInverted return silently once creationLocked is set. That happens on the tween's very first TweenTick and in PrepareAsSequenced, so calling SetLoops or SetAutoKill after the tween has run one frame does nothing and reports no error. Ease, ids, target, update type and time scale are never locked.
  • withCallbacks = false does not suppress OnComplete. In DoGotoInternal only UpdateMode::IgnoreOnComplete blocks it, and both Complete and Goto pass UpdateMode::Goto — so Complete(false), and any Goto that lands on the end, still fire OnComplete (and OnKill after it when auto-kill is on). What the flag actually suppresses is OnStart, OnPlay and OnStepComplete.
  • Complete() returns immediately when loops == -1. An infinite tween can never be completed, only killed — Stop logic that calls Complete() on a looping tween will do nothing at all.
  • Complete() kills the tween when auto-kill is on, which is the default. The handle you kept goes inactive and every subsequent Play, Restart, Goto or Kill early-outs. Call SetAutoKill(false) at creation if you intend to reuse the tween.
  • Restart() does not fire OnStart or OnPlay. It goes through UpdateMode::Goto with playedOnce already true and then sets isPlaying directly, bypassing Play() entirely.
  • Rewind() early-outs when the tween is already at position 0 with 0 completed loops and startup has run, so OnRewind will not fire a second time on an already-rewound tween.

Easing

Easing covers the curve a tween's progress is pushed through: the Ease enum of 38 built-in curves, the two constants that seed the overshoot/period parameters, the EaseFunc funcdef for writing your own curve, the EaseManager namespace that evaluates any curve on demand, and the EaseFactory builders that decorate a curve (currently stop-motion sampling). A curve is normally picked with tween.SetEase(...), but every evaluator here is a plain namespace function you can call directly, which is how you'd draw a curve preview or reuse a formula outside a tween. Most formulas are Robert Penner's, so motion authored in other tweening libraries reads identically here. EaseManager::Evaluate takes raw time and duration in seconds rather than a normalised 0..1 progress, and it divides by duration without guarding against zero.

Picking a built-in curve and feeding it its parameters

// One extra float is the overshoot for the Back curves.

Writing a custom curve and reusing it

angelscript 
using namespace Tweeny;

// Anticipate, then snap: a curve of our own.
float AnticipateSnap(float time, float duration, float overshootOrAmplitude, float period)
{
    float t = time / duration;
    if (t < 0.3f) {
        return -0.15f * (t / 0.3f);
    }
    float rest = (t - 0.3f) / 0.7f;
    return -0.15f + 1.15f * rest * rest;
}

EaseFunc@ anticipate = EaseFunc(AnticipateSnap);
Rotate(transform, 180.0f, 0.6f).SetEase(anticipate);

// A null handle is ignored rather than clearing the ease, so guard it yourself.
if (anticipate is null) {
    Rotate(transform, 180.0f, 0.6f).SetEase(Ease::OutQuint);
}

using namespace Tweeny;

    float progress = float(i) / float(curvePoints.length() - 1);

        DEFAULT_OVERSHOOT, DEFAULT_PERIOD);
}

Things that catch people out

  • EaseManager::Evaluate takes seconds, not normalised progress: time is the elapsed time inside the current loop and duration is one loop's length. Passing a 0..1 progress works only if you also pass duration as 1.0f.
  • Nothing guards duration == 0 — every branch divides by it, so a zero duration yields inf or NaN. Tweens dodge this by rewriting their ease to Ease::INTERNAL_Zero at startup (which returns a constant 1), not by anything Evaluate does.
  • An Ease value with no case in the switch (including Ease::Unset) silently falls through to an OutQuad formula rather than erroring, so a mistyped or newly added enum value looks like it "works".
  • Back and Elastic deliberately return values outside 0..1. If the tweened value is clamped downstream (alpha, a normalised slider), the overshoot is visibly cut off rather than smoothed.
  • For Elastic, period == 0 means "derive it from the duration", not "no oscillation" — In/OutElastic use duration * 0.3 and InOutElastic uses duration * 0.45. And an amplitude below 1 is silently clamped up to 1 with a fixed phase shift, so passing 0.5f does not give you half the overshoot.
  • For the Flash curves, overshootOrAmplitude is the flash *count*, used both as a divisor and cast to int — 0 divides by zero, and fractional values change the final resting value via the decimal-remainder handling in FlashWeighted. period is a weighting roughly in -1..1: positive fades the flashes out over the duration, negative fades them in, and exactly 0 leaves every flash at full strength.

Value-type tweens and the getter/setter contract

Tweeny has no generics, so there is one concrete tween class per animated value type: TweenFloat, TweenInt, TweenVector2, TweenVector3, TweenColor, TweenAngle, TweenRect and TweenString. Each one is driven entirely through a getter/setter pair of funcdef handles: the getter is read once at startup (and per frame for axis-constrained vectors and alpha-only colours) to capture the start value, and the setter receives every interpolated write. All eight expose the same fluent configuration surface (easing, loops, delay, relative, auto-kill, update phase, ids, target, time scale, From, and the eight lifecycle callbacks), each returning its own handle type so calls chain, plus a few options that only make sense for their type: snapping, axis constraints, alpha-only, rotate mode and string scrambling. Tweens are normally created with the Tweeny::To / ToAngle / ToAlpha factories, which call Bind, apply the project defaults and register the tween with the manager.

Things that catch people out

  • A null getter or setter makes startup fail: the tween sets itself inactive and is dropped on its first tick without firing OnComplete or OnKill, so a typo in the funcdef wiring looks like "nothing happened" rather than an error.
  • The start value is captured at startup, not at creation: whatever the getter returns on the first tick (or at ForceInit) is where the tween begins, so a value changed between Tweeny::To and the first frame is silently picked up as the start.
  • From(from, setImmediately = true) calls ForceInit, which runs startup on the spot: the target's current value becomes the tween's END there and then, and the from value is written immediately, so chain From right after creation and before anything else moves the target.
  • Most settings stop working once the tween has ticked (creationLocked) or has been nested in a sequence, and they fail silently: SetLoops, SetDelay, SetRelative, SetSpeedBased, SetAutoKill, SetInverted and From all just return the tween unchanged. SetEase, SetUpdate, SetId, SetTarget and SetTimeScale keep working.
  • SetRelative is also ignored on a From tween (the check is isFrom), so pass the relative flag to From(...) instead of calling SetRelative afterwards.
  • SetSpeedBased reinterprets the duration argument as a speed and the units differ per type: units per second for TweenFloat, degrees per second for TweenAngle, vector length per second for TweenVector2/TweenVector3, the summed absolute RGBA delta per second for TweenColor, and characters per second for TweenString. TweenRect has no SetSpeedBased at all and always uses the literal duration.

Sequences

A TweenSequence plays a group of tweens and callbacks on one shared timeline. Children are placed at absolute positions and seeked there on every update rather than nudged by a delta, so jumping, rewinding and reversing land every child exactly where it belongs with no accumulated drift. Callbacks fire when the window between the previous timeline position and the current one crosses them, in whichever direction the sequence is playing. A sequence is itself an ITween, so it accepts the same playback and lifecycle API as a plain tween and can be nested inside another sequence.

Things that catch people out

  • Composition closes the moment the sequence ticks. The first update sets the creation lock, and with the default auto-play that is the very next frame, so Append, Join, Insert, Prepend, the interval methods, SetLoops, SetAutoKill, SetInverted and the one-time SetDelay all silently do nothing afterwards and just return the sequence -- build the whole thing in one go, or create it paused.
  • Adding a tween takes it over completely: it loses its own delay, its auto-kill and its speed-based flag, it is locked against further configuration, and the manager stops ticking it. Configure a child fully before adding it, and express its offset with Insert(atPosition, tween) instead of a delay on the child.
  • Append, Prepend and Insert reject a null handle, an already-killed tween, and any tween that another sequence already owns -- with no error and no warning, the call just returns the sequence unchanged. Check GetItemCount if you need to be sure a slot was actually created.
  • A child set to infinite loops occupies only one loop's worth of timeline, because the span a child claims is one loop times its loop count and -1 counts as 1. The sequence will cut it off rather than let it loop forever.
  • SetDelay(value) on a sequence is not the plain tween delay: it prepends a real interval, so it shifts everything already added and replays on every loop cycle. Use SetDelay(value, false) when you want the one-shot behaviour a tween has.
  • Callback windows are half-open, and the direction decides which end is open. Going forward, a slot fires when its position is greater than the previous position and less than or equal to the current one -- with the start made inclusive only on the very first update and immediately after a loop wraps, so a callback at position 0 fires once per cycle. Going backwards, slots fire in reverse order for positions greater than or equal to the new position and strictly less than the old one, so a callback sitting exactly at the end does not re-fire when you reverse away from it.

Punch, shake, jump and paths

This area covers the "effect" factories in Tweeny — Punch, Shake, Path, Jump and ToArray — plus the two tween classes they are built on: TweenPath, which walks a value along a linear or Catmull-Rom path at constant speed using a pre-sampled arc-length table, and TweenVector2Array, which walks a Vector2 through a list of waypoints where each segment has its own duration and its own eased curve. All factories take a Vector2Getter@/Vector2Setter@ pair, register the tween with the manager and auto-play it according to the project settings; Punch and Shake additionally treat their waypoints as offsets from wherever the target is when the tween starts. Jump is the odd one out: it returns a TweenSequence built from two TweenFloat tracks (horizontal travel and vertical hops) glued together by an internal JumpDriver, so the arc keeps its shape regardless of distance. Playback control (Play, Pause, Kill, Restart, Goto, Complete, IsPlaying, GetElapsed...) is inherited from ITween/TweenCore and is documented with the core area.

Things that catch people out

  • TweenPath always inserts the target's current position as waypoint 0 before your authored points, so OnWaypointChange indices are shifted by one: index 0 is the start, index 1 is waypoints[0]. The counter also starts at 0, so the move onto your first waypoint is reported like any other.
  • The path is sampled into its arc-length table exactly once, in TweenStartup. SetClosePath, SetRelative and the waypoint list must therefore be final before the first tick — and before any call to PathLength(), PathGetDrawPoints() or ForceInit(), all of which build the path (and capture the target's position as waypoint 0) immediately.
  • PathGetPoint does not force initialisation: called on a tween that has not started it returns the uncaptured start value, i.e. (0,0). Call PathLength() or PathGetDrawPoints() first if you need a point before playback.
  • The resolution / segmentResolution argument only affects PathType::CatmullRom. Linear paths always use one sample per segment, so raising the resolution on a linear path changes nothing.
  • SetSpeedBased on a TweenPath reinterprets the duration you passed to Path()/Bind() as units per second: the real duration becomes pathLength / speed. A speed of 0 or less makes the tween complete instantly.
  • TweenVector2Array requires waypoints.length() == durations.length(). On a mismatch (or a null getter/setter, or an empty waypoint list) TweenStartup returns false and the tween is deactivated on its very first tick without writing a value or firing OnComplete — it fails silently.

Things that catch people out

  • Move is overloaded on the destination type and the two overloads behave differently: Move(t, Vector2(...), d) goes through TransformPlanarAdapter and preserves Z sorting depth, while Move(t, Vector3(...), d) writes all three components and flattens whatever depth the object had. Vector2 also returns TweenVector2@ and Vector3 returns TweenVector3@, so the handle type you store changes with the overload.
  • The single-axis helpers are not really single-axis tweens. MoveX, MoveY, MoveZ, LocalMoveX, LocalMoveY, ScaleX and ScaleY all build a full Vector3 with literal zeros in the unused components and then depend on SetAxisConstraint to stop those zeros being written. If you call SetAxisConstraint(AxisConstraint::None) on the returned tween, or read its end value, you get the zeros.
  • Scale(target, 2.0f, 0.5f) (the uniform float overload) writes Vector3(2, 2, 2) with no axis constraint, so it changes the Z scale too, unlike PunchScale and ShakeScale which go through TransformScaleAdapter and leave the Z scale alone.
  • ShakePosition defaults strength to 3.0 but ShakeScale defaults it to 1.0. Calling them with the same visible argument list produces very different amplitudes.
  • A seed of 0 does not mean "seed zero" — it is the sentinel for "seed from the current unscaled game time", so the default seed = 0 gives a different shake every run. Pass any non-zero value to make a shake reproducible.
  • ShakePosition and ShakeScale hardcode ShakeRandomnessMode::Full, and ShakeCamera additionally hardcodes randomness = 90.0f and fadeOut = true. If you need a harmonic shake or a non-fading camera shake, drop down to the raw Shake(getter, setter, ...) with a TransformPlanarAdapter.

Things that catch people out

  • Fade is an overload set whose return type depends on the target: Fade(Graphic@, ...) returns TweenColor@ while Fade(CanvasGroup@, ...) returns TweenFloat@, so a handle declared with the wrong type will not compile.
  • Tint drives all four colour channels including alpha. If you only want the hue to change, tween Tint and Fade separately, or the graphic will jump to the alpha of the colour you passed.
  • Fade(Graphic@, ...) is built on ToAlpha, which stores Color(0, 0, 0, toAlpha) as the end value and switches the tween to alpha-only mode. Calling .SetAlphaOnly(false) on the returned tween re-enables RGB and the graphic fades to black.
  • AnchorPosX / AnchorPosY work by zeroing the other component of the end value and relying on the axis constraint to suppress it. Calling .SetAxisConstraint(...) yourself afterwards overwrites that constraint and the tween will then also drive the component that was set to 0.
  • Chaining .From() onto AnchorPosX / AnchorPosY destroys the other axis: the from-value is written through the setter directly at startup with no axis constraint applied, so the zeroed component is committed to the rect transform and every later frame re-reads that 0 as the current value.
  • .SetSpeedBased() on an absolute AnchorPosX / AnchorPosY computes duration from the length of the full 2D change vector, which includes the delta to the inert 0 component, so the resulting duration is wrong. Use AnchorPos with an explicit target position for speed-based moves.

Coroutine waits and entity links

This area covers the two ways user code synchronises with a tween's lifetime from outside the tween itself. The six WaitFor* classes implement the engine's ICustomYieldInstruction so a coroutine can block on a tween with Yield(...) until it finishes, dies, rewinds, loops, passes a point on its timeline, or actually begins after its delay. TweenLink and Tweeny::SetLink bind a tween's life to an Entity, applying a LinkBehaviour whenever that entity is enabled or disabled, and always killing the tween once the entity is destroyed. Every wait also releases when its tween is killed, so a coroutine can never be stranded by someone else calling Kill on what it was waiting for.

Coroutine waits

SignatureWhat it does
WaitForCompletion(ITween@ target)Constructs a yield instruction that holds the coroutine until the tween reports complete, but it also releases if the tween is killed, so resuming does not prove the tween actually reached its end.
WaitForKill(ITween@ target)Holds the coroutine until the tween is no longer active; a tween that merely completed with auto-kill disabled stays alive and keeps this wait blocked forever.
WaitForRewind(ITween@ target)Holds until the tween sits at position zero with no completed loops, and additionally requires IsInitialized(), so a tween that has never been ticked keeps the coroutine waiting even though its position is already zero.
WaitForElapsedLoops(ITween@ target, int elapsedLoops)Holds until GetCompletedLoops() reaches elapsedLoops; only finished cycles count, so a loop in progress never satisfies it.
WaitForPosition(ITween@ target, float targetPosition)Holds until GetElapsed(true) reaches targetPosition in seconds, which counts every finished loop and excludes the start delay, so on a looping tween the value is measured along the whole accumulated timeline rather than inside the current loop.
WaitForStart(ITween@ target)Holds until the tween has captured its start value (IsInitialized()), which is how you wait out a configured delay and act on the frame the tween really begins.

Wait protocol

SignatureWhat it does
bool CanContinue()The ICustomYieldInstruction hook implemented by all six wait classes, polled by the coroutine scheduler each tick and returning true when the coroutine may resume; it also returns true when the stored tween handle is null or inactive, which is what makes every wait kill-safe.

LinkBehaviour::PauseOnDisableRestartOnEnablePauses on disable and calls Restart(true) on re-enable, replaying the delay from the beginning.

Examples

Sequencing a cutscene by waiting on each tween in turn, including waiting out a delay

angelscript 
using namespace Tweeny;

void PanelIntro(Entity@ leftPanel, Entity@ rightPanel)
{
    Yield(WaitForCompletion(Tweeny::MoveY(Transform::Get(leftPanel), 0.0f, 0.6f).SetEase(Ease::OutBack)));

    TweenVector3@ rightSlide = Tweeny::MoveY(Transform::Get(rightPanel), 0.0f, 0.6f);
    rightSlide.SetDelay(0.4f);

    Yield(WaitForStart(rightSlide));
    Debug::Log("[ui] the right panel just started moving");
    Yield(WaitForCompletion(rightSlide));
}

Waiting on loop count and on a point along the accumulated timeline

angelscript 
using namespace Tweeny;

void PulseRoutine(Transform@ icon)
{
    TweenVector3@ pulse = Tweeny::Scale(icon, 1.4f, 0.5f);
    pulse.SetLoops(-1, LoopType::Yoyo);

    // three finished cycles; a cycle in progress does not count
    Yield(WaitForElapsedLoops(pulse, 3));

    // 4.5s of total elapsed time, loops included and delay excluded

    pulse.Kill(false);
}

Things that catch people out

  • Every wait releases when its tween is killed or its handle is null. That is deliberate (a coroutine can never be stranded), but it means resuming after WaitForCompletion does not prove the tween finished. If the distinction matters, check IsComplete() yourself after the Yield.
  • WaitForKill and WaitForCompletion are not opposites. Complete leaves a tween alive when auto-kill is off, so WaitForCompletion releases while WaitForKill keeps blocking; only an actual Kill releases WaitForKill.
  • WaitForRewind requires IsInitialized() as well as position zero. A freshly created tween that has never been ticked is at position zero but not initialized, so the wait blocks instead of releasing immediately as you might expect.
  • WaitForPosition compares against GetElapsed(true), which sums every finished loop and ignores the start delay. On a looping tween the target is a point on the whole accumulated timeline, so a value smaller than one loop duration can only ever be hit during the first loop.
  • TweenLink.Evaluate primes itself on its first call: it records the entity's enabled state and returns without acting. Linking a tween to an entity that is already disabled therefore does not pause or kill it — the behaviour only fires on a change of enabledInScene.
  • The destroy guard is not optional and is not the same as LinkBehaviour::KillOnDestroy. Any behaviour kills the tween with Kill(false) once the entity is null or fails Object::IsValid, so the end value is never applied on destruction, whatever behaviour you picked.

Examples

A yoyo flash on the PostUpdate phase, with a custom easing function and lifecycle callbacks

angelscript 
using namespace CometEngine;
using namespace Tweeny;

class HealthFlash : CometBehaviour
{
    private float flash = 0.0f;
    private int halfCycles = 0;

    void Start()
    {
        Tweeny::To(FloatGetter(this.GetFlash), FloatSetter(this.SetFlash), 1.0f, 0.25f)
            .SetLoops(6, LoopType::Yoyo)
            .SetUpdate(UpdateType::Late)
            .SetEase(EaseFunc(SmoothStepEase))
            .OnStepComplete(TweenCallback(this.OnHalfCycle))
            .OnComplete(TweenCallback(this.OnFlashDone));
    }

    private float GetFlash() { return flash; }
    private void SetFlash(float value) { flash = value; }
    private void OnHalfCycle() { halfCycles++; }
    private void OnFlashDone() { flash = 0.0f; }
}

float SmoothStepEase(float time, float duration, float overshootOrAmplitude, float period)
{
    float t = duration <= 0.0f ? 1.0f : time / duration;
    return t * t * (3.0f - 2.0f * t);
}

Things that catch people out

  • LoopType::Yoyo does nothing unless the tween actually loops: the inversion is guarded by "loops > 1 || loops == -1", so SetLoops(1, LoopType::Yoyo) just plays forward. SetLoops also silently rewrites its count — 0 becomes 1, and anything below -1 becomes -1 (infinite).
  • AxisConstraint::None means "write every component", not "write none", and the flags start at 2 (X = 2, Y = 4, Z = 8, W = 16) so there is no bit-0 value; combine them with | and cast back, e.g. AxisConstraint(AxisConstraint::X | AxisConstraint::Y).
  • Axis constraints are only honoured when a getter is bound, because the skipped components are read back from the getter; with a null getter every component is written regardless of the constraint. Only TweenVector2 (X, Y) and TweenVector3 (X, Y, Z) consult the constraint at all — TweenColor, TweenRect and the array/path tweens ignore it, and nothing reads AxisConstraint::W.
  • UpdateType::Manual tweens are never advanced by the engine; they only move when Tweeny::ManualUpdate(deltaTime, unscaledDeltaTime) is called. PrepareForPreview also forces a tween onto Manual, so a previewed tween stops responding to the normal phases.
  • LoopType::Incremental works by pushing the eased value above 1 (it adds the completed loop count), so the writer extrapolates. TweenString clamps the eased value to 0..1 before revealing characters, which makes Incremental behave like Restart there, and TweenColor does not clamp its channels, so an incremental colour tween drives them out of range.
  • UpdateNotice::RewindStep is raised for LoopType::Restart wraps and when the tween sits at position 0 with no completed loops — it is not raised for a Yoyo turnaround. Custom tween types built on TweenCore must treat it as "the timeline just jumped back", which is exactly what TweenSequence uses to rewind its children.

Settings, runner, the no-code component and the editor tools

This area covers how Tweeny boots and how it is configured, plus the parts a designer touches instead of writing code. TweenySettings is a ProjectSetting the engine instantiates on its own: it holds the project-wide defaults for new tweens, pushes them onto the singleton TweenyManager, and creates the immutable runner entity that ticks tweens every frame. TweenyAnimation is a CometBehaviour that exposes the same feature set as inspector fields, building and driving one tween from Play/Pause/Rewind/Kill. The editor side is TweenyPreview, which plays live tweens outside play mode and restores their targets afterwards, driving the two menu windows (Tweeny Inspector and Ease Gallery), alongside the small TweenyRandom generator and the version constant.

Examples

Attaching and driving a TweenyAnimation from script — set the fields first, because Play is what reads them.

angelscript 
using namespace CometEngine;
using namespace Tweeny;

class ChestLid : CometBehaviour
{
    private TweenyAnimation@ bounce;

    void Start()
    {
        @bounce = TweenyAnimation::Add(entity);
        if (bounce is null) {
            return;
        }
        bounce.animationType = TweenyAnimationType::PunchScale;
        bounce.endValueVector = Vector2(0.3f, 0.3f);
        bounce.duration = 0.4f;
        bounce.vibrato = 12;
        bounce.elasticity = 0.6f;
        bounce.autoPlay = TweenyAutoPlayMode::Manual;
    }

    void Open()
    {
        bounce.Play();

        ITween@ running = bounce.GetTween();
        if (running !is null && running.IsActive()) {
            Debug::Log("lid punch started");
        }
    }
}

Slow motion through the manager, and restoring the project defaults afterwards.

angelscript 
using namespace CometEngine;

class SlowMotion : CometBehaviour

        manager.unscaledTimeScale = 1.0f;
    }
}

A custom editor window that previews every live tween and puts the scene back when it closes.

angelscript 
using namespace CometEngine;
using namespace CometEditor;
using namespace Tweeny;

[MainMenuItemWindow("Tools/Shake Preview", "Shake Preview")] class ShakePreviewWindow : EditorWindow
{
    private TweenyPreview preview;

    void OnGUI()
    {
        if (!preview.IsPreviewing()) {
            if (GUI::Button("Preview every tween")) {
                array<ITween@>@ live = Tweeny::AllTweens();
                for (uint i = 0; i < live.length(); i++) {
                    preview.Add(live[i]);
                }
            }
            return;
        }

        float delta = Time::GetUnscaledDeltaTime();
        preview.Update(delta > 0.25f ? 0.25f : delta);

        GUI::Text("previewing " + preview.GetCount() + " tweens   "
            + formatFloat(preview.GetElapsed(), "", 0, 2) + "s");
        if (GUI::Button("Stop and restore")) {
            preview.Stop(true);
        }
    }

    void OnDestroy()
    {
        preview.Stop(true);
    }
}

Things that catch people out

  • TweenyAnimation reads its inspector fields only inside Play, which rebuilds the tween from scratch: changing duration, ease or loops on a running animation has no effect until you call Play again.
  • Play kills the current tween first and then captures the entity's current transform values as the new start, so replaying mid-flight starts from wherever the entity happens to be, not from the original pose. Pause followed by Play is not a resume.
  • The punch and shake animation types go through a separate configuration path that applies only loops, loopType, delay and autoKill — ease, relative, from and ignoreTimeScale are silently ignored for them, and the shake seed is not exposed at all, so component shakes cannot be replayed exactly.
  • Fade and Tint fail silently: if rendererTarget is empty and BaseRenderer::Get(entity) finds nothing, the build returns null, Play leaves the internal handle at null and nothing at all happens.
  • For LocalMove and Scale the component builds a Vector3 from endValueVector plus the transform's current Z, so local Z position and Z scale are never animated; Move uses the planar overload and likewise preserves sorting depth.
  • globalTimeScale multiplies the unscaled delta too (unscaled = unscaledDeltaTime * unscaledTimeScale * globalTimeScale), so tweens marked timescale-independent still freeze when you set the global time scale to 0. Use unscaledTimeScale for those.
